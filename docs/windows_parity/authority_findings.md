# Windows authority audit: source-level triage

Status: **no Windows security or utility parity claim**. This is a pinned source audit, not a complete runtime call graph or an installed-artifact test. The Mac checkout and Phantom sign-in/signing/key code were not changed.

`authority_audit.json` records every one of the 337 path-literal candidates and 136 literal built-in contracts in `source_inventory.json`, plus 34 contracts composed into the builtin list from `core/code_assistant/contracts.py` and `core/repoops/contracts.py`. It also records 853 lexical direct-effect leads from production Python modules, 13 method-level HTTP census rows with no matching path literal, and four dynamic/background rows, including the native broker CLI. Generate/check it with `python -m tools.windows_authority_audit --write` and `--check`. `--release-check` must fail while unresolved rows remain.

Current status: **0 authenticated, 0 brokered, 3 narrowly safely disabled, 1,374 unresolved** across those categories. The new `/companion` literal is a presentation-only loopback GET route, but its installed native-host boundary is not yet proven, so its row remains unresolved. The disabled paths are `sandbox.run_command` on native Windows (`core/runtime_execution_tools.py:3440-3441`, `sandbox/sandbox_runner.py:68`, `sandbox/job_runner.py:575-604,643-658`), the explicit `browser.render` unavailable stub (`core/runtime_execution_tools.py:3024-3040`), and the native Windows `confined_argv` fallback used by plugin/MCP launch (`core/plugin_executor.py:264-277`). Those refusals are not functionality parity, and they do not clear alternative execution paths.

First control-gate slice: the Windows bundle sends one per-launch, 32-byte secret over anonymous child stdin pipes to the API and window (`installer/bundle/bundle_supervisor.py`, `core/native_control.py`). Both the Starlette and legacy HTTP handlers require a method/path/body-bound, short-lived, single-use proof for state-changing `/api/mode` and `/api/commands/dispatch` requests. A missing pipe prevents bundle child startup; API replacement rotates the secret and stops the old window. The Inno script now selects the native WebView2 host (`installer/windows_host/`) as the installed entrypoint, and that host adds a native review dialog before signing those two requests. The produced internal artifact is unsigned and not yet installed-artifact tested. Therefore neither route is `authenticated` in this ledger: signed-host behavior, a complete approval trace and other effect paths remain unproven. The Python-window fallback remains a utility gap, not parity.

Independent review no-go findings: the guard activates only when `VOOL_WINDOWS_BUNDLE=1`; a second unbundled server using the same user data is not excluded by this source-level gate, so installed host/data isolation remains unproven. The installed Python-window page calls are unsigned, and there is no signed installed-artifact test of the candidate WebView2 approval gesture. A nonzero window startup failure such as missing WebView2 currently retries while API/Ollama remain alive; the installer/repair journey needs a terminal failure state and clean shutdown. The JSON handlers now cap bodies before allocating an unbounded request and have positive/negative tests for both transport adapters, but installed-artifact availability/DoS evidence is still absent.

Native broker prototype, 2026-09-20: `installer/windows_broker/` builds with .NET 10. The prior local self-contained probe harness passed 14/14 component checks on this Windows 11 development host, exercising a low-integrity AppContainer with no capabilities, Job limits, scratch-only file access, denied loopback, inherited-handle filtering, argument quoting, timeout/cancellation, descendant termination, and rejection of executable/ancestor symlinks. Source staging opens from a fixed-volume handle with `OBJ_DONT_REPARSE` and copies from that held handle. A test in `installer/windows_broker/tests/Program.cs` requires a sharing-violation denial for staged-file rename and write access, then checks the path and payload hash. The current source permits the rename; the harness therefore **fails 1 of 16 tests** as a security no-go. Retaining the writable staging handle prevented the rename but made `CreateProcessW` fail with a sharing violation, so that unsuccessful implementation was removed. The staged image is still launched by path from same-user-writable scratch, and scratch cleanup still recursively inspects and deletes by path. Neither same-user replacement race is closed. The broker executable itself is unsigned, is not in the installed VOOL package, is not called by Python or the native host, and accepts only staged `.exe` payloads without the JSON stdin, scoped workspace, script entrypoints, variable network/timeout and approval policies needed for VOOL command/plugin parity. Its CLI remains unresolved in the ledger; no tool or route is promoted to `brokered`.

Architecture decision required: a documented `CreateProcessW` call selects its image by pathname, not by an already verified file handle. Retained no-write/no-delete handles and handle-relative scratch operations can mitigate ordinary swaps, but the current same-user ACL permits a process with that SID to pre-hold writable/delete-capable handles, so they do not prove the strict same-user boundary. A broker running under a separately protected Windows principal with a private staging ACL is one strong route, but provisioning a service/principal can require elevation and would change the agreed non-admin, per-user installation contract. A second design candidate is a signed, fully packaged MSIX with an immutable broker/helper executable launched from its OS-protected package location, passing tasks as data rather than staging arbitrary EXEs under the user's ACL. [Microsoft's packaged-desktop documentation](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes) says per-user package files are read-only and OS-protected; it does **not** establish that this candidate can preserve VOOL's command/plugin utility, isolation policies, direct-download experience, or the current `VOOL.exe` host contract. MSIX therefore needs a separate feasibility spike and clean Win10/Win11 proof before it can replace the service option. Do not choose an elevated-service expansion or promote either candidate to broker parity from this document. Hash checks followed by path-based launch, suspended start, or inherited-handle allowlists are not substitutes for image identity. Scratch cleanup independently needs handle-relative, bounded, no-follow create/enumerate/delete; no path-recursive fallback is acceptable.

Protected-image/MSIX spike, 2026-09-20: the native broker gauntlet now passes 16/16 source-host tests, including AppContainer/low-integrity identity, exact Job limits, scratch-only write access, host-file read/write denial, loopback network denial, inherited-handle denial, timeout/cancellation cleanup, reparse/UNC denial, staged-image rename/write denial, System32 launch, child containment and descendant termination. The executable replacement fix keeps a no-delete handle through a hash-verified transition into a read-only launch lock. This proves the launcher primitive on this development host, not installed VOOL effect routing. The Inno payload now contains `VOOL.exe`, the broker, embedded Python, Ollama and the Microsoft-signed offline WebView2 installer, but only an unsigned, dirty-tree, `release:false` internal artifact has been produced. It has not been installed in the clean VM. Protected application effects have not yet converged on the broker, and neither signed package immutability nor Win10/Win11 installed behavior, full utility, update or rollback is proven.

Installed-package surrogate, 2026-09-20: on this Windows 11 host, `Get-AppxPackage` reports `Microsoft.DesktopAppInstaller_1.29.290.0_x64__8wekyb3d8bbwe` as Store-signed, and the installed `winget.exe` has valid Authenticode. The standard-user process could obtain neither write nor DELETE access to that file. The test-only direct launcher nevertheless received Win32 error 87 (`ERROR_INVALID_PARAMETER`) from `CreateProcessW` when it supplied the existing custom AppContainer attributes; using a neutral System32 working directory did not change the result. This is a **failed package-image launch gate**, not proof that every purpose-built MSIX helper is impossible: `winget.exe` is itself a declared full-trust package application. Do not weaken the zero-capability token or promote the MSIX design from this surrogate. An installed VOOL helper built as package content still needs its own direct-launch and negative-policy tests. No trusted signing certificate or clean Windows 10/11 VM was available on this host, and no package or certificate was installed. Full MSIX utility additionally requires the native `VOOL.exe` host, fixed WebView2 runtime instead of Inno's imperative runtime installer, model seeding into `%LOCALAPPDATA%`, protocol activation, and a Windows package updater; current source does not provide that end-to-end path (`installer/bundle/vool.iss`, `installer/bundle/bundle_supervisor.py`, `installer/windows_host/VoolWindow.cs`, `core/updater/platforms.py`).

Verification on this host: the broker/test project builds with zero warnings; the base harness passes 15 and fails its staged-image swap security gate. With the optional Store-package surrogate, it passes 15 and fails both the swap gate and the direct package-image launch gate. The focused cumulative Windows Python slice previously passed 106 with 28 skipped; a later broader Windows-focused slice passed 63 with one skipped. A broader 12-file slice additionally failed one pre-existing shell-bootstrap contract assertion (`tests/test_bootstrap_install_contract.py`) unrelated to the broker. Repository-wide `pytest -q` stopped at collection with 31 errors, including missing `tzdata` and `playwright`, platform-incompatible `os` imports, and Windows default-encoding failures. None of these results substitutes for clean-VM installed-artifact testing.

## What the counts mean

- The 337 are **string candidates**, not 337 confirmed executable routes. `tools/windows_parity_inventory.py:24-40` scans all matching string constants. The method-aware command census finds 293 HTTP rows across 280 paths; 267 paths overlap this candidate set. The remaining 70 static candidates include possible delegated leaves, data keys and false positives; 13 census-only method rows are also recorded. `/{path:path}` is a Starlette catch-all, while `/api/pull` in `core/web/api/runtime.py` is an Ollama pull URL, not a VOOL route.
- Starlette transport is in `core/web/api/app.py`; real GET/POST dispatch is in `core/web/api/service.py` and delegated handlers. The ledger records source occurrence, enclosing function, a selecting `if` and syntactic branch calls where found, plus method/owner/effect/test metadata from `core/command_registry/census.py`. An absent selecting branch is **not** proof of unreachability; prefix, constant and dynamic dispatch need manual/runtime proof.
- Of 136 literal contracts, 111 have a syntactic `_dispatch_runtime_tool` branch or `vool-browser.*` prefix dispatch lead in the ledger. The other 25 need external-lane or dynamic handling review. `core/runtime_tool_contracts.py:2955-2957` also composes 9 `code.task.*` and 25 `repo.*` contracts; the 136 seed alone was incomplete. Contract-side `approval_requirement` and `side_effect_class` are declarations, not enforcement.
- The 853 effect rows are lexical leads, not 853 confirmed bypasses: 670 filesystem mutations, 115 process launches and 68 network sends. The scan now includes descriptor-based `os.open` writes, `os.write`, and direct `sock.connect` calls as well as common path and HTTP calls in `apps`, `core`, `sandbox`, `installer`, `network` and `relay`. It cannot see native code, third-party libraries, dynamic method dispatch, all HTTP client wrappers or complete transitive caller chains. Every sink remains unresolved until its caller, authority, policy, receipt and installed behavior are checked.

## Release rule

No unresolved row earns a Mac/Windows parity claim. A row can move to `authenticated` or `brokered` only with exact source enforcement, negative tests, and evidence from the **installed signed Windows artifact**. `safely_disabled` requires a fail-closed test and honest UI capability reporting; it is a containment state, not equivalent utility. `--release-check` remains a hard no-go until an installed-artifact attestation verifier is implemented; filling the evidence fields with strings cannot clear it. The current ledger intentionally blocks release rather than laundering `OperatorAuthority`, an Origin check, a declared opt-in, or a method-level census classification into proof.
